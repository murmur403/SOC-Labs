
# SOC-003 — SSH Brute-Force Detection

## Objective

Investigate repeated SSH authentication failures in a controlled laboratory environment using Wazuh SIEM.

The goal of this lab is to identify suspicious authentication activity, analyze security alerts, correlate events with MITRE ATT&CK techniques, and document the investigation from a SOC Analyst Level 1 perspective.

## Lab Environment

| Component | Description |
|---|---|
| SIEM | Wazuh 4.14.0 |
| Monitored endpoint | Kali Linux |
| Wazuh Agent | `murmur-kali` (ID: 001) |
| Agent IP | `192.168.100.20` |
| Wazuh Manager IP | `192.168.100.10` |
| Attack simulation | Repeated failed SSH authentication attempts |
| Source IP | `127.0.0.1` (localhost) |
| Target account | `murmur` |
| Log source | `journald` |

All authentication attempts were performed locally in an isolated, authorized lab environment.
## Investigation Methodology

### 1. SSH Service Configuration

The SSH service was configured to listen only on the loopback interface (`127.0.0.1`), preventing external connections during the simulation.

The configuration was verified using:

```bash
sudo ss -lntp | grep ':22 '
```

### 2. Controlled Authentication Attempts

Two SSH sessions were initiated from the Kali Linux terminal:

```bash
ssh -o PubkeyAuthentication=no murmur@127.0.0.1
```

Three intentionally incorrect passwords were entered during each session, producing six failed authentication attempts.

### 3. Local Log Verification

The authentication failures were verified using:

```bash
sudo journalctl -u ssh --since "30 minutes ago" --no-pager | grep "Failed password"
```

The logs confirmed six failed password attempts from `127.0.0.1`, targeting the `murmur` account.

### 4. SIEM Analysis

The Wazuh Threat Hunting dashboard was used to investigate authentication events generated by the `murmur-kali` agent.

Two Wazuh rules were examined:

- **Rule 5760 (Level 5):** SSH authentication failure.
- **Rule 2502 (Level 10):** Multiple authentication failures reported by the system.

The alerts were analyzed using timestamps, source IP addresses, target usernames, original log messages, and MITRE ATT&CK mappings.
## Findings & Evidence

### Finding 1 — SSH Authentication Failures

Six failed SSH authentication attempts were recorded across two local SSH sessions.

Wazuh generated six individual alerts associated with the test:

- **Rule ID:** `5760`
- **Rule Level:** `5`
- **Description:** `sshd: authentication failed.`
- **Source IP:** `127.0.0.1`
- **Target User:** `murmur`
- **Agent:** `murmur-kali`

These events confirmed that the SIEM detected the failed authentication attempts.

### Finding 2 — Multiple Authentication Failures

Wazuh also generated two Rule `2502` alerts during the SOC-003 simulation.

- **Rule ID:** `2502`
- **Rule Level:** `10`
- **Description:** `syslog: User missed the password more than one time`
- **MITRE ATT&CK:** `T1110 — Brute Force`
- **MITRE Tactic:** `Credential Access`

One original log entry contained:

```text
Nov 23 00:00:51 kali sshd-session[100043]: PAM 2 more authentication failures; logname= uid=0 euid=0 tty=ssh ruser= rhost=127.0.0.1 user=murmur
```

The Rule 2502 alerts were triggered by PAM messages reporting multiple authentication failures. They do not independently establish that Wazuh correlated several Rule 5760 alerts through a frequency-based detection rule.

### Finding 3 — SIEM Storage and Visibility Issue

During the investigation, newly generated alerts were initially absent from the Wazuh Dashboard despite being recorded by the Wazuh Manager.

The investigation identified:

- A full server filesystem (`100%` utilization).
- Filebeat errors reporting `no space left on device`.
- Approximately 12 GB of temporary vulnerability-feed update data under `/var/ossec/queue/vd_updater/tmp`.

After a controlled cleanup of the temporary update files and restoration of the Wazuh Manager, approximately 11 GB of disk space became available.

The Filebeat connection test succeeded, and the Dashboard subsequently displayed the previously missing SSH alerts.

This demonstrated how infrastructure resource exhaustion can affect SIEM alert visibility.
